# SBF / VBF / SBZ1 フォーマット仕様 (再解析版)

- 作成日: 2026-11-12 (ブランチ `re_analyze`)
- 解析対象 (製品版の全データ):
  - PC: `SEGA Rally Revo_HCJ` — `.sbf` 1201 本 + `livery23_data_sbf` 1 本 = **1202 本**
  - PS3: `NPJB90076/USRDIR` — `.sbf` 743 本 + `.vbf` 815 本 + `livery55_data_BK_vbf` 1 本 = **1559 本**
  - 計 **2761 アーカイブ / 76,319 ブロック**
- 検証スクリプト: [`tools/sbf_inspect.py`](../tools/sbf_inspect.py)
  (`--validate <dir>` で本書の規則を全件チェックする。標準ライブラリのみで動作)

本書の規則には、全件で成立したもの (✅) と、少数の例外があるもの (⚠) がある。
⚠ のものは、例外の件数と内容を併記する。
従来の `CLAUDE.md` にある「ContainerHeader 0x1C + ExtraHeader 0x28」というモデルは、
**偶然バイト数が合っていただけで、構造の解釈としては誤り**だった (§9)。

## 1. 全体像

```
SBZ1 (任意)  ── zlib で包む外殻
└ SBF/VBF
   ├ グローバルヘッダー (0x18)
   ├ エントリーテーブル (8 × count)
   ├ パディング (0x1000 境界まで)
   └ ブロック × count   ← 再配置可能なリソース 1 個 = 1 ブロック
        ├ ブロックヘッダー (0x14)
        ├ 内部ポインタ再配置テーブル (reloc)
        ├ 外部参照テーブル (import)
        ├ データ本体 (size バイト)
        └ type 固有トレーラ (type 5 のみ)
```

1 アーカイブは、ハッシュで識別されるリソース (モデル・マテリアル・シェーダ・テクスチャ・
データ表など) の集合である。各リソースは**メモリにそのまま置いてポインタを補正するだけで
使える再配置可能ブロック**になっている。

### プラットフォームによる違い

| | PC | PS3 |
|---|---|---|
| エンディアン | リトル | **ビッグ** (`.sbf` も `.vbf` も BE) |
| `.sbf` の中身 | 全 type (テクスチャ含む) | **type 4 以外**すべて (メインメモリ側) |
| `.vbf` の中身 | — (存在しない) | **type 4 (テクスチャ) のみ** (VRAM 側) |
| 分割 | なし | `.vbf` は約 2MB ごとに `name.vbf`, `name.1.vbf`, `name.2.vbf` … に分かれる |

PS3 の `name.sbf` と `name.vbf` (分割があればそのすべて) のブロックハッシュを合わせると、
PC の `name.sbf` のハッシュ集合と一致する (共通する 603 アーカイブのうち 594 件)。
**PS3 版は、PC 版と同じリソース群を「メインメモリ用 (.sbf)」と「VRAM 用 (.vbf)」に
分けて格納したもの**である。名前ハッシュもプラットフォーム間で共通。

> 拡張子でエンディアンは判断できない。`sbf_inspect.py` は +0x00 (3/4) と
> エントリー先頭の type の妥当性から自動判定している。

## 2. SBZ1 (圧縮外殻)

| オフセット | 型 | 内容 |
|---|---|---|
| +0x00 | char[4] | `"SBZ1"` (両プラットフォームともこのバイト列。エンディアン変換なし) |
| +0x04 | u32 | 展開後サイズ (**プラットフォームのエンディアン**: PC=LE / PS3=BE) ✅ |
| +0x08 | … | zlib ストリーム (RFC1950)。EOF まで |

- 圧縮率: PC 850/1202、PS3 1159/1559 が SBZ1
- zlib ヘッダーは `78 9C` (標準レベル)。例外は各プラットフォーム 1 件ずつの `78 DA`
- 展開結果の長さは +0x04 と全件一致 ✅

## 3. グローバルヘッダー (0x18)

| オフセット | 型 | SBF | VBF | 意味 |
|---|---|---|---|---|
| +0x00 | u32 | 3 / 4 | 3 / 4 | **フォーマット (ビルドツール) バージョン**。§8 |
| +0x04 | u32 | 0 | 0 / 1 | VBF のみ: **続きの分割ファイルがある**ことを示すフラグ (⚠ 後述) |
| +0x08 | u32 | 0 | ≠0 | VBF のみ: **メインメモリに置く部分の長さ** (= ブロックヘッダー群の終端) ✅ |
| +0x0C | u32 | 0 | 0 | 常に 0 ✅ |
| +0x10 | u32 | 0 | 0 | 常に 0 ✅ |
| +0x14 | u32 | count | count | ブロック数 |

- VBF +0x08 は、非空なら `0x1000 + 0x44 × count`、空 (count=0) なら `0x18` ✅ (816/816)。
  どちらも「ここまでがヘッダー、以降はテクスチャ実データ」の境界になっている
- VBF +0x04: 分割ファイル群のうち、**次の番号のファイルが存在するもの**は 65 件すべてで 1。
  例外は 2 種類ある
  - 「次がある」のに 0 のものが 7 件。`skoda_ftarmac_model.2.vbf` が `.1.vbf` と同一内容
    であるなど、残骸ファイルと思われる
  - バージョン 3 の VBF は 84 件すべてが 1 (次のファイルは無い)。v3 では意味が異なる可能性がある

### エントリーテーブル (+0x18, 8 × count)

| オフセット | 型 | 内容 |
|---|---|---|
| +0x00 | u32 | ブロックの名前ハッシュ (ブロックヘッダー +0x04 と常に同値 ✅) |
| +0x04 | u32 | ブロックの先頭オフセット (ファイル先頭から) |

- エントリーはオフセット昇順に並ぶ ✅ (ハッシュ順ではない)
- 最初のブロックは `roundUp(0x18 + 8 × count, 0x1000)` 以降に置かれる ✅
  (テーブルが長い track 系では先頭が 0x3F3C などになる)

## 4. ブロック (コンテナ) 構造 — 再配置可能リソース

**全 76,319 ブロックで、次の構造が隣接ブロックにはみ出さずに成立した** ✅

```
+0x00  u32  type                 リソース種別 (§5)
+0x04  u32  nameHash             名前ハッシュ (§7)
+0x08  u32  size                 データ本体のバイト数
+0x0C  u32  sub                  type 固有の補助値 (type 5 / 12 以外は 0)
+0x10  u32  nReloc
+0x14  u32  reloc[nReloc]        データ内の「内部ポインタ」フィールドのオフセット (データ先頭基準)
       u32  nImport
       u32  import[nImport]      データ内の「外部参照 (ハッシュ)」フィールドのオフセット
       u8   data[size]           データ本体 (ヘッダー長 = 0x18 + 4 × (nReloc + nImport))
       ...  type 5 のみトレーラ (§6.5)
```

### 4.1 内部ポインタ再配置 (reloc)

- `reloc[i]` はデータ先頭からのオフセット (4 の倍数)。その位置の u32 には
  **データ先頭からの相対オフセット**が入っている。ロード時に基底アドレスを加算して
  ポインタ化するものと考えられる
- 値 `0xFFFFFFFF` は **NULL** (補正しない)。範囲外の値はすべてこれだった ✅
  (type 11 の 27 万件、type 5 の 9 千件など)
- それ以外の値は常に `0 ≤ v ≤ size` ✅

### 4.2 外部参照 (import)

- `import[i]` が指す位置の u32 には、**参照先リソースの nameHash** が入っている。
  ロード時にハッシュから実体ポインタへ解決されるものと考えられる
- 値 0 は「参照なし」
- 解決先 (0 以外の 297,343 件)
  - 同一アーカイブ内のブロック: 約 90%
  - 別アーカイブ (共有テクスチャ、ShaderLib など): 約 10%
  - どのブロックのハッシュにも一致しないもの: 1,170 件。これは**すべて** type 13
    (テクスチャパック) が定義する「差し替えスロット」のハッシュだった (§6.13)
  - → **すべての import がいずれかに解決できる** ✅

### 4.3 型ごとの参照関係 (import 先の type)

```
 1 Model        → 2 (Material)
 2 Material     → 3 (Shader, データ +0x00 に必ず 1 件) / 4 (Texture) / テクスチャパックのスロット
 6 ParticleInfo → 1
11 SceneGraph   → 1
12 TypedObject  → 1, 4, 5, 6, 11, 12
13 TextureList  → 4
 5 DataTable    → 任意 (1,2,3,4,5,6,7,11,12)
 3 / 4 / 7      → なし
```

## 6. type 固有の構造

### 6.4 type 4: Texture

データ本体 (`size` バイト) = **0x2C の記述子 + DDS ファイル (0x80 ヘッダー + ペイロード)**。
このため `size = ミップ全段の合計 + 0x2C + 0x80 = ミップ合計 + 0xAC` になる。
nReloc = nImport = 0 なので、ブロックヘッダーは 0x18 バイトで、記述子は +0x18 から始まる。

| データ内 | 型 | 内容 | 根拠 |
|---|---|---|---|
| +0x00 | u32 | 種別: 1 = 2D、2 = キューブマップ | 2 の 57 件はすべて DDS caps2 = 0xFE00 (全 6 面) |
| +0x04 | u32 | データポインタ (PC = 0、PS3 VBF = 論理オフセット §6.4.2) | ✅ |
| +0x08 | u32 | 幅 | DDS ヘッダーと全件一致 ✅ |
| +0x0C | u32 | 高さ | 同上 ✅ |
| +0x10 | u32 | 常に 0 | |
| +0x14 | u32 | AddressU (1 = Wrap, 3 = Clamp) | D3DTEXTUREADDRESS と同じ値。PS3 の一部は 0x2901 (= GL_REPEAT) |
| +0x18 | u32 | AddressV (同上) | |
| +0x1C | u32 | AddressW (常に 1。PS3 の一部は 0x2901) | |
| +0x20 | u32 | フィルタ (2 = Linear, 3 = Anisotropic) | D3DTEXTUREFILTERTYPE と同じ値 |
| +0x24 | f32 | ミップ LOD バイアス | 0.0 / 0.05 / 0.3 / -0.25 / -2.0 / -3.0 … |
| +0x28 | u32 | 最大異方性 (1〜8) | |

従来ツールの呼び方との対応は次のとおり。「ContainerHeader +0x18」がこの記述子の +0x00、
「ExtraHeader +0x00〜+0x24」が記述子の +0x04〜+0x28 にあたる。

#### 6.4.1 PC (SBF) での配置

ブロック先頭から 0x18 + 0x2C + 0x80 = **+0xC4 にある DDS ペイロードが 0x1000 境界**に来るよう
ブロックを配置する (⚠ 例外は 56 件: `*_model.sbf` の 55 件と `livery68_data.sbf` の 1 件。
これらは前ブロックの直後に詰めて置かれる)。
典型的な先頭位置 `0x1F3C` は `0x2000 - 0xC4` である。

#### 6.4.2 PS3 (VBF) での配置

VBF ではブロックヘッダー + 記述子 (0x18 + 0x2C = **0x44**) だけを先頭に並べ、
DDS 本体はその後ろの領域に置く。PS3 の非空 VBF 全 637 本 / 4,050 テクスチャで次の規則が
成立した (例外 1 件は §10)。

```
0x0000  グローバルヘッダー + エントリー
0x1000  ブロック k のヘッダー + 記述子 (0x44)  … k = 0..n-1   ← ここまでが +0x08
        ゼロ埋め
H_0     DDS ヘッダー[0] (0x80, dword 単位でバイト反転 = マジック " SDD")
H_0+80  ペイロード[0]  (0x1000 境界。バイトスワップ無し)
        ゼロ 0x44 バイト
        ゼロ埋め (次ペイロードの 0x1000 境界まで)
H_1     DDS ヘッダー[1] ...
        最終ペイロードの直後が EOF (末尾のゼロ 0x44 も無い)
```

- `H_0 + 0x80 = roundUp(+0x08, 0x1000) + 0x1000` ✅ (637/637)
- `H_{k+1} = roundUp(H_k + 0x80 + payloadLen_k + 0x44 + 0x80, 0x1000) - 0x80`
- **記述子 +0x04 (データポインタ) = `H_k - 0x1018 - 0x44 × k`** ✅ (4049/4050)
  - 物理位置からテクスチャ 1 枚ごとに 0x44 ずつ引いた値であり、実ファイル上のオフセットではない
  - 0x44 はちょうど「ブロックヘッダー + 記述子」の長さである。各ペイロード後のゼロ 0x44 は、
    PC と同じ配置 (ヘッダー → DDS) を組んでからヘッダー部分だけを先頭へ移した跡
    (空の席) と解釈できる

### 6.5 type 5: DataTable

- データ本体: 4 バイト単位の値の並び (int / float / ハッシュ参照 / 内部ポインタ)。
  ハッシュ参照は import に、ポインタは reloc に登録される
- **トレーラ**: データ本体の直後に必ず存在する ✅

```
u32  0                         (常に 0)
u32  nSymbol
{ u32 nameOffset; u32 valueOffset; } [nSymbol]   ← どちらもデータ先頭基準
char names[]                   NUL 終端文字列の連続
```

- `sub` (+0x0C) が 0 なら nSymbol = 0。0 以外なら `sub == size` で、シンボル表を持つ ✅
  (PC 505 件 / PS3 454 件すべて)
- シンボル名は `<リソース名>.data.<フィールド名>` 形式。
  例: `livery36.data.Body_Texture` → valueOffset 4 (値は Texture の nameHash)
- シンボル表を持たない DataTable (大多数) は、フィールド名がビルド時に捨てられている。
  意味は値の並びとゲームコードから推測するしかない
- データ先頭 (data_offset) は 16 バイト境界に揃えられる ✅

### 6.7 type 7: RawFile

- nReloc = nImport = 0。データ本体はファイルの中身そのもの (エンディアン変換されない)
- 判明した中身: Granny2 `.gr2` (PC 1,111 / PS3 154)、XML (`*_xml_file.sbf` ほか)、
  `system_data` の UTF-16BE 言語テーブル、zlib 圧縮ブロック (`78 9C` で始まるもの)
- データ先頭は 8 バイト境界 (⚠ 例外は 4 バイト境界の PC 26 件 / PS3 23 件)

### 6.12 type 12: TypedObject

- `sub` = クラス (構造体型) のハッシュ。PC 78 種類
- データ本体はそのクラスのシリアライズ。参照は import / reloc で表現される

### 6.13 type 13: TextureList (テクスチャパック)

`*texturepack{dust,mud,snow}_xdata` に入っている。

```
u32 1
u32 count
{ u32 textureHash;  u32 slotHash; } [count]   ← textureHash 側が import に登録される
```

- textureHash は同じアーカイブ内の type 4 (差し替え後のテクスチャ)
- **slotHash は Material (type 2) が import している「仮想テクスチャ名」**。
  どのブロックのハッシュにも一致しない import 1,170 件は、すべていずれかの slotHash だった
- → 路面状態に応じてテクスチャパックを読み込み、Material のスロットを実テクスチャに
  差し替える仕組みと考えられる

### 6.1 / 6.2 / 6.3 / 6.6 / 6.11

ブロック層 (reloc / import / size) までは確定している。データ本体の内部構造は未解析。
テクスチャやシェーダの差し替え・データ表の編集だけなら、この層の知識で足りる。

## 7. 名前ハッシュ

- 32 ビット。PC と PS3 で同一のリソースは同じ値になる
- ゲームはリソースをハッシュで検索し、文字列名は DataTable の値などに残るだけ
  (例: `"SegaRallyLogo"` → Model の nameHash)
- **ハッシュ関数は未特定**
  - 名前文字列が判明している 611 組 (シェーダ名、XML 名、DataTable のリソース名) に対し、
    CRC32 の各種バリエーション、FNV-1/1a、djb2、sdbm、Jenkins one-at-a-time、
    MurmurHash2、ELF、x31/x131/x65599 を、大文字小文字・パス付き・拡張子の有無を
    変えて試したが一致しなかった
  - ビルド時に、元アセットのフルパスなど本書の範囲では得られない文字列から計算された可能性が高い
  - PC 版 EXE の `.text` は SafeDisc で暗号化されていて (関数プロローグが 1 件も見つからない)、
    静的解析での特定はできなかった
- 実用上の影響: **リソースを差し替えるときは既存のハッシュを流用すればよい**。
  新しい名前のリソースを追加することは、現状できない

## 8. 配置・パディング規則 (パッカー実装用)

全 SBF (PC 1202 / PS3 743) で確認した。

1. 最初のブロック: `roundUp(0x18 + 8 × count, 0x1000)` 以降に置く ✅
2. 各ブロックは前ブロック終端 (type 5 はトレーラ終端) 以降で、
   **データ先頭 (= ブロック先頭 + 0x18 + 4 × (nReloc + nImport)) が次の境界に揃う最小位置**に置く

   | type | 揃える対象 | 境界 |
   |---|---|---|
   | 4 | DDS ペイロード (データ先頭 + 0xAC) | 0x1000 |
   | 5, 11 | データ先頭 | 16 |
   | 7 | データ先頭 | 8 |
   | その他 | データ先頭 | 4 |

   ⚠ 規則どおりでないブロックが 85 件 (全体の約 0.1%) ある。
   多くは規則より 4〜0x14 バイト多い隙間 (type 11 の後の type 5、particle 系の type 6 など)。
   一部は境界を満たさずに前ブロックの直後へ詰めて置かれている (type 7 など)。
   ローダーは境界さえ満たせば位置を問わないと考えられるが、未検証
3. ファイル末尾
   - **v4**: `EOF = roundUp(最終ブロック終端, 4) + 0x800` ✅ (PC 1094 / PS3 659)
   - **v3**: `EOF = roundUp(最終ブロック終端, 0x800)` ✅ (PC 108 / PS3 84)
4. パディングの中身
   - **v4**: すべてゼロ ✅
   - **v3**: ゼロとは限らない。ビルドツールのメモリ残骸と思われるゴミが入る
     (ヘッダー部のパディングを含む)

### バージョン 3 と 4 の違い

- ブロック層の構造は同一。違いはパディングのゼロ埋めと EOF 規則だけである
- v3 は旧ビルドのアセット (PC: liveries の一部、cubemap、一部の車種モデル) で、
  Material の典型サイズが違う (v3 0x4A8 / v4 0x738) など、**データ本体の構造体
  レイアウトが古い**可能性がある

## 9. 従来の解釈 (CLAUDE.md) との対応

| 従来の呼び方 | 実際の構造 |
|---|---|
| ContainerHeader (固定 0x1C) | ブロックヘッダー 0x14 + reloc 表 + import 表 (**可変長**)。0x1C になるのは nReloc = nImport = 0 で、かつデータ先頭の 1 dword を含めた場合だけ |
| ContainerHeader +0x0C | `sub` (type 5 = シンボル表オフセット、type 12 = クラスハッシュ) |
| ContainerHeader +0x10 | nReloc |
| ContainerHeader +0x14 | reloc[0] または nImport |
| ContainerHeader +0x18 | reloc/import の続き、またはデータ先頭 (type 4 なら記述子 +0x00 = 種別、type 7 ならファイル先頭 4 バイト) |
| ExtraHeader (0x28, type 4) | テクスチャ記述子 (0x2C) の +0x04〜+0x2B |
| ExtraHeader +0x00 (VBF の論理オフセット) | 記述子 +0x04 = データポインタ。`H_k - 0x1018 - 0x44k` |
| ExtraHeader +0x0C〜+0x24 「固定値」 | 0 / AddressU / V / W / フィルタ / LOD バイアス / 最大異方性 |
| テクスチャ間の 0x44 gap | VBF で先頭へ移したヘッダー + 記述子の空き席 |
| type 5 = 「グループ/インデックス」 | 名前付きパラメータ表 (+ 任意のシンボル表) |
| PC パディング規則 `roundUp(0x7C + linearSize, 0x1000)` | §8 の規則 (type 4 は +0xC4 のペイロードを 0x1000 境界へ) |
| グローバル +0x04 「0/1 のフラグ」 | VBF の分割継続フラグ |
| グローバル +0x08 | VBF のメインメモリ部の長さ |

現行ツールはブロックを不透明バイト列として扱っているため、ラウンドトリップは成立している。
ただし次のような操作を正しく行うには、本書のモデルに沿った実装が必要になる。

- PC 版のテクスチャのサイズ変更 (アラインメントの再計算)
- type 5 のフィールド編集 (シンボル表による名前 → オフセットの対応)
- Material が参照するテクスチャの付け替え (import の値の書き換え)
